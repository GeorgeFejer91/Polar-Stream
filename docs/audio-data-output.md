# Experimental audio data output

## Short answer

Data can be encoded into an audio waveform, recorded, and decoded later. That
operation is **modulation/encoding**, not encryption. Polar Stream's current
audio toggle does not provide secrecy, authentication, or tamper resistance.
Anyone with the format can decode a clean recording.

The implementation is intended for a stereo digital loopback or a line-level
AUX/USB audio cable. It is not claimed to work reliably through a phone speaker
and microphone, a voice call, a lossy audio codec, a mono headset microphone,
or an input with automatic gain control/noise suppression.

## Why this design

The H10's nominal raw payload is already about 1,590 bytes/s before framing:

- ECG: 130 samples/s × 3 bytes = 390 bytes/s;
- ACC: 200 samples/s × 3 axes × 2 bytes = 1,200 bytes/s.

Small-message acoustic libraries are therefore too slow. For example,
[ggwave](https://github.com/ggerganov/ggwave) documents FSK, Reed–Solomon error
correction, browser/WASM examples, and only 8–16 bytes/s. It remains a good
candidate for short pairing codes, not continuous raw H10 data.

[Quiet Modem](https://quiet.github.io/docs/quiet/how/) demonstrates the more
general solution: frame synchronization, CRC, forward error correction, and
GMSK/PSK/QAM/OFDM modulation over speakers/microphones or a cable. It is useful
prior art, but its browser stack is old and substantially heavier than this
application needs. The telephone-channel [ITU-T V.34
standard](https://www.itu.int/rec/T-REC-V.34) is another established example of
audio-band data transmission at up to 33.6 kbit/s.

Polar Stream therefore implements a small dependency-free, cable-oriented
link rather than importing an unmaintained browser modem:

- stereo Manchester PCM;
- 11,025 symbols/s on each channel, carrying 22.05 kbit/s in aggregate;
- 125 ms input batching;
- a per-frame preamble, schema/type byte, 16-bit sequence number and CRC32;
- compact signed 24-bit ECG and signed 16-bit X/Y/Z ACC payloads;
- UTF-8 metric identifiers with 32-bit floating-point values;
- a bounded 1.25-second scheduled-audio horizon; falling behind stops the
  output visibly instead of growing memory without a limit.

Manchester coding is DC-balanced and simple to reacquire after the short
silence between frames. CRC32 rejects corrupted frames; it does not repair
them. A future speaker/microphone mode should use a proper synchronized modem
with forward error correction and measured device/channel profiles.

## Recording and decoding

1. Connect the playback device to a true **stereo** line input or select a
   stereo digital loopback recorder. Many phone TRRS microphone inputs are mono
   and will not work; a class-compliant USB-C audio interface is usually the
   clearer phone option.
2. Record uncompressed stereo PCM at 44.1 or 48 kHz. Disable voice processing,
   noise suppression, echo cancellation, automatic gain control, spatial audio,
   and lossy compression.
3. Keep levels below clipping. The generated waveform uses ±0.22 full scale,
   leaving headroom.
4. Decode the WAV file:

   ```bash
   python3 scripts/decode_audio_data.py recording.wav
   ```

   The decoder writes `recording.decoded.csv` and accepts `--threshold` when a
   quiet line input has changed the recorded gain. Only CRC-valid frames are
   exported.

The automated browser validation builds a waveform with the production
JavaScript encoder, writes a stereo PCM WAV, runs the reference Python decoder,
and verifies the recovered ECG, ACC, and metric rows.

## Packet format

All integers are little-endian. Bytes within the audio bitstream are sent most
significant bit first; successive bits alternate between left and right audio
channels.

```text
audio preamble: 55 55 55 55 55 55 55 55 D3 91

packet:
  magic                 2 bytes   "PS"
  schema/type           1 byte    high nibble schema, low nibble frame type
  sequence              2 bytes
  payload length        2 bytes
  payload               N bytes
  CRC32                  4 bytes   covers packet before CRC

batch payload:
  section count         1 byte
  repeated sections:
    section type        1 byte    1 ECG, 2 ACC, 3 metrics
    sample/value count  2 bytes
    final sensor time   8 bytes   nanoseconds; zero when unavailable
    section length      2 bytes
    section payload     N bytes
```

The raw section timestamp is the final PMD sample time. The decoder reconstructs
earlier timestamps at the configured 130 Hz ECG or 200 Hz ACC rate. Metric
sections currently have no sensor timestamp.

## Reliability and lifecycle boundaries

The native CSV writer is the reliable persistence path: it receives raw data in
Rust after immediate LSL/OSC publication and uses a bounded 128-notification
writer queue. Audio generated by the native WebView is experimental and can
miss display-channel events; it is not an authoritative replacement for CSV,
LSL, or OSC.

On the website, [Chrome's Web Bluetooth
support](https://developer.chrome.com/docs/capabilities/bluetooth) works in
supported secure Chromium contexts, including Chrome on Android, after an
explicit device chooser. The site requests a screen wake lock while connected.
This protects a visible foreground session when the browser and battery policy
allow it, but does not make background capture reliable. [Web Bluetooth is not
available in Web Workers](https://developer.mozilla.org/en-US/docs/Web/API/Web_Bluetooth_API),
[screen wake locks require an active visible
document](https://developer.mozilla.org/en-US/docs/Web/API/Screen_Wake_Lock_API),
and Chrome's [Page Lifecycle](https://developer.chrome.com/docs/web-platform/page-lifecycle-api)
permits a hidden page to be frozen or discarded. Switching apps, changing tabs,
or locking the screen can therefore interrupt Bluetooth, CSV, and audio capture.
A native app with an Android foreground service is required for a guaranteed
screen-off or background recording workflow.
